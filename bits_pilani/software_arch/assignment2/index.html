Activity 1

Identify top 3 Architecturally Significant Requirements (ASRs) and write them in the form of a Utility tree. Why are these architecturally significant?

My application is an AI Decision Engine (AIDE) for credit card companies, that approves or declines transactions, credit card requests, credit limit increase requests, etc.

Description of how the system works

  • AI Decision Engine (AIDE) acts as the universal point of contact for all AI-model related decisioning. It exposes several APIs for internal as well as external use.
  • It works by identifying the type of request, and appropriately calls the relevant machine learning model on those input parameters to generate model scores, which are then consumed back by AIDE to make the final decision.
  • Internal use cases involve an application team performing some analysis and wanting to run a model for their inputs, and analyzing the outputs.
  • External use cases involve a commercial merchant hitting the API to authorize a customer transaction, eg: a customer swipes card at a petrol station, the card machine (POS terminal) from the petrol station will hit the AIDE API to validate the transaction.

The top three ASRs are:

  1. Security
  2. Performance
  3. Availability

Activity 2

Describe in detail, the tactics you recommend for each ASR. For example, if caching is a tactic you recommend, please mention what you will cache, what tool you would use, how it will work, etc.

The tactics I would use for each ASR are:

  • Security
    • Machine Learning – We use machine learning to detect fraud and unauthorized use of our systems
    • Firewall – We use a “block all unless whitelisted” approach on our firewall that ensures that all connections are setup for a reason, and all internal systems are isolated from public facing internet by default.
    • Resist and react to attacks to maintain system integrity, like access revocation for identified actors
  • Performance
    • Load balancing – There are dedicated load balancers that ensure no one system is overwhelmed
    • Containerization – We use a containerized architecture, orchestrated by Kubernetes which allows us to dynamically scale up individual services whenever needed
    • Demand forecasting – We use AI models that can help us forecast demand ahead of time based on historical data, which allows the systems to seamlessly scale, as required.
  • Availability
    • Redundancy – There are multiple redundant systems so a fault in one system will not bring down the entire network
    • Cloud – We use an in-house cloud that allows us to easily manage our application deployments in different regions, ensuring customers don’t face downtime
    • Fault detection and recovery – Systems are able to detect faults and recover from them by restoring to last known stable configuration

Activity 4

Indicate important messages between components by labelling the connections in the C&C view. Also indicate the communication method used.

Throught the process, most communication happens via the following methods:

  1. Procedure Calls – The front-end user interface component could make procedure calls to the AIDE server component to submit credit card applications and retrieve decisions. The AIDE server component also makes procedure calls to the AI model component to process application data and return decisions. These procedure calls are also used for the microservices to interact with each other, as and when required.
  2. Shared Data – The AIDE server component and the AI model components access and modify a shared database to store and retrieve applicant data and decisions. Even some other systems such as the enterprise model management and approval systems share access to the database to review decisions and make adjustments as necessary.
  3. Event Broadcasting – The AIDE server component broadcasts information to other components when certain events happen, for example, when a credit card application is submitted or when a decision is made. The other components like the fraud detection system, could listen for these events and take action when they occur.

Activity 5

Draw a sequence diagram for one major scenario (use case). Mention the scenario.

Following is the sequence diagram for a new credit card decisioning process:

The scenario here is explain below:

  1. User opens the application form on their browser and enters the details such as which credit card they are interested in, their credit bureau identifier (ITIN, similar to PAN number in India which is used to pull CIBIL reports from Transunion Credit Bureau), their age, and other documention.
  2. This request reaches AIDE server which decides which AI model to use depending on the request type. Given this is a new credit card application request from a client in the US, it choses the appropriate model designated for these scenarios.
  3. The AI model receives the request from AIDE server along with all the input parameters it has received from the user. This particular model also needs the FICO score, and it determines that it needs to be requested from the credit bureau, so it requests a FICO score based on the ITIN number.
  4. Credit bureau returns the FICO score for the given ITIN number.
  5. The model is now executed on the input parameters including the FICO score and a decision is generated
  6. The decision is returned to the user’s browser for their information.

Activity 6

State the architectural patterns used. Explain, where in the architecture, these patterns have been used.

The following architectural patterns have been used in AIDE:

  • Microservices Pattern – This pattern is used to break down the application into small, independent services that communicate with each other through RPCs (Remote procedure call). For example, one service is responsible for collecting data from credit card applicants, second service is responsible for take live income transaction data and making a decision, and a third service is responsible for communicating the decision to the applicant. This allows for greater flexibility and scalability as each service could be developed and deployed independently. This is especially useful because not all services face the same load at all times, for example, the service for aggregating data runs jobs in batch mode, while the second and third services handle real-time traffic. In addition, each single type of AI model used acts as an independent service, because the load varies on each type of model throughout the day. For example, the fraud detection model is used at all times, for all transactions and all login attempts, but the credit limit decisioning model only runs when a limit decision is required, either at time of new application, or later.
  • Event-Driven Pattern – This pattern is used in AIDE to instantly start services in response to events. The process of gathering data and analysing it begins when a credit card application is made. Once a choice has been made, another event is set off that notifies the prospective customer of the choice. This allows the decisioning of credit card applications to happen more quickly.
  • Layered Pattern – We use this to separate responsibilites between the different layers of AIDE. For example, one layer is responsible for collecting data from credit card applicants, another layer is responsible for analyzing the data and making a decision, and a third layer is responsible for communicating the decision to the applicant. This allows for greater modularity and maintainability as each layer is developed and maintained independently by us.
  • Client-server Pattern – This is used to separate the front-end user interface from the back-end processing and decision-making. The backend server is what invokes different services, that may even be running on separate hardware. We use an Apache WSGI webserver for the backend, and an Angular application for the frontend for this particular application.
