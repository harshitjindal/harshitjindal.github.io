Problem Statement

The high level objective is to design and implement a service-based application for any application of choice. The task can be broken down into the following parts.

Design

Design a service-oriented architecture and define the REST API endpoints for the application of your choice.

  • Identify the basic capabilities of the application based on the core practical use case of the application.
  • Once the different entities and models in the application are figured out, split them into individual resources and describe them.
  • Name the resource and define the operations that can be performed for each resource.
  • For each operation, design the URI and choose the appropriate HTTP method and headers required.
  • Design the representation(s) accepted by the client and the representation(s) served to the client.
  • Categorize the resources based on their type.

Implementation of Service Endpoints

For the service-oriented architecture and the REST API endpoints for the application designed in Part 1, Implement a functional prototype of the application of choice, demonstrating its key requirements.

Choose the core important resources defined in Part 1 and implement them.

API Gateway

As part of the implementation process for the service-oriented application, the task is to design and develop an API Gateway that acts as a single entry point for all client requests and routes them to the corresponding services.

The API Gateway should be a central component to handle routing and ensure seamless communication between clients and the underlying services.

Depending on the application design, authentication may be handled at the API gateway or other methods may be used.

Custom API gateways may be created that satisfy basic needs like routing or use open-source API gateways or cloud provider API gateways.

Methodology

To achieve the aforementioned goals of this assignment, in addition to my love for animals, an application for a dog walking service called Doggie Go Walkie is built based on a service oriented architecture.

The purpose of the application is to allow pet parents to be able to ensure their beloved pets get the right amount of mental stimulation and physical exercise even if they are unable to take them out for walks on some days due to temporary busy-schedules or medical problems. With Doggie Go Walkie, they can do so by hiring other dog lovers to take their dogs out for walks and to play with them, ensuring the pets’ needs are met regardless of factors such as the owners being busy or no longer being physically able to do so themselves, such as for older people.

To build the backend services for this application, the following tech stack is used:

  • Programming Language: Python 3.9
  • Backend Framework: Flask 3.0.0 and a custom implementation of JWT from scratch for authentication
  • Cloud Providers: Python Anywhere for hosting
  • Database: SQLite for persistent storage of application data

The detailed list of all the dependencies along with their versions used in the project is available in the requirements.txt file in the GitHub Repo for this project at https://github.com/harshitjindal/Doggie-Go-Walkie.

The Flask application has also been deployed to https://harshitjindal.pythonanywhere.com/ and can be tested via Postman, as demonstrated in the Demo.

Basic Capabilities

The basic capabilities for Doggie Go Walkie are listed below:

    • Create new account
    • Login and logout of the account
    • Schedule a walk
    • View scheduled walks
    • Cancel a walk
    • Track a walk

  2. Walker Role:

    • Start and end walk sessions

In the context of a RESTful API design, resources typically represent the key entities that the system manages. In the DoggieGoWalkie application, walks can also be considered as resources.

Representations:

Representations Accepted by the Client (Request Bodies):

  • These are the data formats that the client sends to the server when making requests.
  • Request bodies typically contain information that the server needs to perform a specific operation or action.
  • The client constructs these representations to communicate its intentions to the server.
  • Examples include data sent when creating a new user, scheduling a walk, or updating information.

Representations Served to the Client (Response Bodies):

  • These are the data formats that the server sends back to the client in response to a request.
  • Response bodies contain the results of the requested operation or information requested by the client.
  • The server constructs these representations to provide feedback, data, or status to the client.
  • Examples include data returned when retrieving user information, viewing scheduled walks, or confirming the completion of a walk.

User Login

@app.route('/users/login', methods=['POST'])
def login_user():
    login_data = request.get_json()

    access_token = ''.join(random.choice(string.ascii_uppercase) for _ in range(12))

    for user in users:
        if user["username"] == login_data["username"] and user["password"] == login_data["password"]:
            user["access_token"] = access_token
            return jsonify({"access_token": access_token}), 200

    return jsonify({"error": "Invalid username or password"}), 401

Part 2.2: API Gateway

The API Gateway is implemented with Flask, which supports routing by creating encapsulating functions with @app.route decorators. For example, the API Gateway is running for this application at https://harshitjindal.pythonanywhere.com/ or localhost:5000 by default when the execution instructions are followed to run the code locally.

This gateway then supports routing to various URIs, such as (details URIs are defined above in the design section):

  • https://harshitjindal.pythonanywhere.com/users to create user account.
  • https://harshitjindal.pythonanywhere.com/users/login to login to an existing user account and generate the access_token required for all privileged actions.
  • https://harshitjindal.pythonanywhere.com/users/{userid}/logout to logout user.
  • etc.

The core component ensuring that the application works safely is authentication, which is to validate if the user is actually who they say they are. For example, if a user is trying to login to account with username john, they need to prove that they are the ones that own that account by providing the password associated with it.

The way authentication has been implemented in this application is by using tokens. When a user first creates an account, their user data gets stored at the backend. Now, once they try to login using the same credentials (username and password) that they used at the time of account creation, a token gets generated for them. This token is then expected to be used to authenticate them for all subsequent actions such as scheduling a walk, etc. When the user wishes to logout, this token is again used to ensure a random person cannot logout any other person without permission.

Once logout action is performed with the correct token, the token becomes invalidated and cannot be used for any further actions until it is regenerated using the login action. All of this, of course, happens at the frontend framework, and is NOT done explicitly by the user, but is handled by the frontend application. For our testing, we use Postman to demonstrate this.

Creation of new user account

User with username harshitjindal1 is created.

Creation of user that already exists

User with username harshitjindal1 already exists.

User login with correct credentials

An access_token is generated when login was attempted with correct credentials.

User login attempt with incorrect credentials

An error is thrown when login is attempted with incorrect credentials.

User logout with correct access_token

The access_token is invalidated once logout action is performed with the correct access_token. This also means this same token cannot be used to perform logout operation again.

User logout attempt without correct access_token

Without the correct access_token, it cannot be invalidated. This is to protect someone logging out another user.

Performing arbitrary action without correct access_token

Without the correct access_token, no information can be viewed that might be confidential to another user. For example, I cannot view another user John's scheduled walks, or track a walk without the correct access_token.
