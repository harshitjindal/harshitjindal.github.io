Problem Statement

ABC organization would like to opt for the distributed version control system to upgrade their environment, where Git has been selected as the solution. You been assigned as a consultant to educate the migration process to move their source code from centralized to distributed systems. As phase one, you would like to go ahead with a workshop to demonstrate below operations to make the ABC team comfortable:

  1. Create a repository
  2. Add two directories and some raw code files to the repository
  3. Move code from one directory to the other directory
  4. Update one source code file and display the difference
  5. Create a branch (feature-branch)
  6. Add some raw code to feature-branch
  7. Merge feature-branch into main
  8. Push changes to GitHub

At the end, provide the summary of advantages of moving from centralized source code to distributed version control.

Methodology

As a one-time setup to perform the assignment effectively, an empty directory assignment1 is created on my local machine. In addition to this, a remote repository is created on GitHub which can be found at https://github.com/harshitjindal/devops-assignment-1

I have documented each of the steps listed under the problem statement with a list of git commands as and when they are first introduced, along with the explanation and screenshot(s).

Steps

1. Create a repository

Git Commands:

  • git init: used to initialise a new git repository within a directory

We take the local directory assignment1 and execute git init on it to initialise it as a git repository. This creates a .git subdirectory that git uses to maintain this local repository.

We then go to github.com and create a new remote repository.

Git Commands:

  • git remote add <remote_name> <remote_link>: Used to create a new remote

It’s time to link our local and remote repositories. We can do this by adding a remote (essentially a link to our GitHub repository) for our local repository.

In our case, we execute git remote add origin https://github.com/harshitjindal/devops-assignment-1.git on the local machine. This sets up the remote with name origin, and can be validated with git remote -v.

2. Add two directories and some raw code files to the repository

Git Commands:

  • git add: used to start tracking files, and to stage changes
  • git commit: used to commit the staged changes
  • git status: used to view which files are untracked, tracked, and staged for commit

We create two directories dir1 and dir2, and then add two files dir1/file1.py and dir2/file2.py with some dummy content for demonstration purpose.

We then track the new files and stage the changes using git add and commit them with git commit. We can use -m option with git commit to pass the commit message in the same command.

3. Move code from one directory to the other directory

We move file1.py from dir1 to dir2.
Similarly, we move file2.py from dir2 to dir1.

This essentially mimics the process of moving code from one directory to another. Once the files are interchanged, we stage the files (already tracked) with git add <filename>, and commit with git commit -m <commit_message>.

4. Update one source code file and display the difference

Git Commands:

  • git diff: used to display delta for files or commits

We append a dummy line of code to dir2/file1.py to demonstate the way we can view the difference. To do this, we run git diff <filename> before staging, or git diff --cached <filename> after staging the changes. The lines in green prepended with a + symbol represent new additions, and lines in red prepended with - symbol represent deletions.

Generally, if a line / block of code is modified, the old changes would show up as deleted, and the new changes would appear like new additions. For example, a line the quick brown fox, if changed to the quick brown fox jumps over the lazy dog would show up in a diff as follows:

-the quick brown fox (in red)
+the quick brown fox jumps over the lazy dog (in green)

5. Create a branch (feature-branch)

Git Commands:

  • git branch: used to create a new branch
  • git checkout: used to switch to an existing branch

We create a new branch feature-branch. Normally, we first create a new branch like git branch feature-branch and then switch to it with git checkout feature-branch.

However, there’s a shorter way using -b option for git checkout, like git checkout -b <branch_name> which creates a new branch and then switches to it.

6. Add some raw code to feature-branch

We create a new directory some_dir_for_feature, and within it a new file feature.py with some content. As we did before, we start to track and stage this new file with git add <filename>, and then commit with git commit.

It is worth noting that . can be used as a wildcard with git add, ie: git add . would track and stage all files that are either untracked, modified, or both. It is always a good practice to run git status before and after running git add to prevent accidents.

7. Merge feature-branch into main

Git Commands:

  • git merge: used to merge branches
  • git log: used to view the history / a timeline of commits

We move to the main branch with git checkout main. We then run git merge feature-branch to move the changes from feature-branch into main branch.

What we have here is called a fast-forward merge, which happens when the destination branch (main in this case) has no commits that aren’t already present in the incoming branch (feature-branch in this case), and the tip of the destination branch simply moves forward to the latest incoming change. This does NOT create a merge commit, and maintains linear history.

Git provides a lot of flexibility with different types of merges (fast-forward, two-way, three-way), and even rebase functionality which always maintains linear history at the expense of regenerating commit SHAs (changing history). Git can usually identify the type of merge required, but we can also explicitly let it know what type we prefer for any particular scenario, for example, we can let Git know that we want to merge only if a fast-forward is possible with the --ff-only option.

8. Push changes to GitHub

Git Commands:

  • git push: used to push local commits to a remote repository

It’s time to push our committed changes from the local repository to the remote repository on GitHub. We can easily do this with git push <remote_name> <branch_name>.

In most cases, however, it is convenient to only have to execute git push instead of explicitly mentioning remote_name and branch_name. We can easily achieve this by setting the upstream branch for any local branch with the -u option. For example, we can run git push -u origin main while we are on the main branch, and the next time onwards we only need to run git push for main branch.

It is worth noting that upstream is automatically set for branches that are pulled to local repository from a remote repository with git pull.

Advantages of DVCS over CVCS

  1. Because each developer has their own copy of code, they can work offline. This is in contrast to having to constantly stay connected to the server, as in the case of centralized source code.

  2. Faster and more efficient, because operations can be performed on local machines, and then later pushed / pulled to the version control server, when required.

  3. Multiple levels of redundancy, because each developer would have a copy of the code on their system, even if the main server loses its copy, it can easily be recovered.

  4. Much better branching support, where each new feature can have its own branch, which can be tested in isolation with each other and then later merged into the main branch once ready.

  5. More convenient because developers don’t need to fetch each other’s changes before making their changes. The sync can happen in a single go later, and not necessarily constantly.
